Energy Efficiency Concepts & Strategy

Our Energy Optimization Strategy for Smart City Sensor Network

1. Duty-Cycling (ContikiMAC)

Nodes sleep most of the time (>99%).

Wake up periodically to check for transmissions.

Reduces idle listening energy dramatically.

Synchronization-free operation.

2. Power Monitoring with PowerTracker

Real-time tracking of CPU, LPM, Tx, Rx time.

Per-node energy consumption analysis to identify power-hungry nodes or behaviors.

Export CSV for offline analysis.

3. Adaptive Control

Remote duty-cycle adjustment via commands.

Reduce sampling rate for low-battery nodes.

Prioritize critical nodes (e.g., near border router).

Balance network coverage vs. energy consumption.

4. Energy-Aware Design

Lightweight JSON packets minimize Tx time.

Use UDP instead of TCP to avoid overhead.

6LoWPAN header compression saves bytes.

Batch processing reduces wake-up frequency.

# Slide: Experimental Results

**1. Data Collection**
- 30,286 sensor readings from 21 nodes over 5-hour simulation
- 1,260 energy samples (PowerTracker, 5-minute intervals)
- 3 duty-cycle commands issued to degraded nodes
- Packet loss: 4–10% (1-hop) to 10–40% (during burst interference)

**2. ML Failure Prediction**
- Model: RandomForest (80 trees, max_depth=10)
- Features: environmental readings + rolling averages (NO raw battery_mv)
- Overall accuracy: 94.6%
- Failure class: Precision 89.4%, Recall 73.2%, F1 80.5%
- Healthy class: Precision 95.4%, Recall 98.4%, F1 96.9%
- The model predicts failure 50 readings ahead (~8 min) purely from sensor patterns

**3. Energy Efficiency**
- ContikiMAC duty-cycling: 5.6x reduction in radio-on time vs always-on
- Nodes spend >99% of time in Low-Power Mode (LPM)
- Healthy nodes maintain battery above 2500 mV for entire 5-hour run
- 2-hop nodes consume ~30% more energy than 1-hop (relay overhead)

# Slide: Limitations & Future Work

**Honest Limitations**

1. **Simulation-only**: All data comes from Cooja simulator, not real hardware.
   Sensor readings use randomized values with temporal patterns, not actual
   PM2.5/temperature/noise sensors.

2. **Synthetic data for ML training**: The training data is generated by a
   Python script that models realistic patterns (diurnal cycles, spatial
   correlation, sensor drift). Real-world data would have additional noise,
   concept drift, and edge cases that could reduce accuracy.

3. **Energy measurements are simulated**: ContikiMAC duty-cycling is real
   (built into Contiki-NG), but our PowerTracker numbers come from the
   simulator's timing model, not physical hardware measurements.

4. **No real-world deployment**: The mesh network topology, radio
   propagation, and interference patterns are simplified models.

**Future Work**

1. Deploy on real hardware (e.g., Zolertia RE-Mote, nRF52840 DK) with
   actual PM2.5, temperature, and noise sensors.

2. Implement MQTT or CoAP for standardized IoT messaging.

3. Add TLS/DTLS security for data-in-transit encryption.

4. Scale to 100+ nodes and test multi-DODAG RPL scenarios.

5. Collect real-world data and retrain ML model — expected accuracy
   would likely be 75–85% due to noisier real sensor readings.

6. Add edge computing: run lightweight ML inference directly on
   constrained nodes for in-network anomaly detection.
